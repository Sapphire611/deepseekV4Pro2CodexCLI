§1

启动与配置

代理启动时最先做的事情：加载 .env 文件中的 API Key。不把密钥硬编码在源码中是安全基础。

JavaScript 

const http = require('http');
const https = require('https');
const fs = require('fs');
const path = require('path');

// 加载 .env 文件1
function loadEnv(filePath) {
  if (!fs.existsSync(filePath)) return;
  const content = fs.readFileSync(filePath, 'utf8');
  for (const line of content.split('\n')) {
    const trimmed = line.trim();
    if (!trimmed || trimmed.startsWith('#')) continue;
    const eqIdx = trimmed.indexOf('=');
    if (eqIdx === -1) continue;
    const key = trimmed.slice(0, eqIdx).trim();
    const val = trimmed.slice(eqIdx + 1).trim();
    if (!process.env[key]) {
      process.env[key] = val;2
    }
  }
}
loadEnv(path.join(__dirname, '.env'));

const PORT = 8099;
const DEEPSEEK_HOST = 'api.deepseek.com';
const DEEPSEEK_KEY = process.env.DEEPSEEK_KEY;3

if (!DEEPSEEK_KEY) {
  console.error('❌ 未设置 DEEPSEEK_KEY');
  process.exit(1);4
}
注解 1

手写 .env 解析器

不依赖 dotenv 包，用 20 行实现一个精简版。逐行读取，跳过空行和 # 注释，按 = 分割键值对。零依赖 = 零安装。

注解 2

环境变量优先

if (!process.env[key]) — 只在环境变量未设置时才从 .env 取值。这意味着你可以用 DEEPSEEK_KEY=xxx node proxy.js 覆盖文件中的值。

注解 3

硬编码已移除

Key 只从环境变量读取。如果 .env 文件和环境变量都没有设置，程序会报错退出，不会悄悄发空请求。

注解 4

Fail-fast

没有 Key 就没有必要继续运行。process.exit(1) 立即终止，不会启动一个注定失败的 HTTP 服务。

§2

角色映射

OpenAI 的 Responses API 使用 developer 角色（比 system 更高级的系统消息），但 DeepSeek 的 Chat Completions API 只认 system。一行映射解决兼容性问题。

JavaScript 

/** DeepSeek 不支持的角色 → 映射为 system */
const ROLE_MAP = { developer: 'system' };5
function mapRole(role) {
  return ROLE_MAP[role] || role;
}
注解 5

可扩展的映射表

目前只需映射 developer → system。如果将来有其他不兼容角色，直接在 ROLE_MAP 对象中添加即可。|| role 保底：未知角色原样透传。

§3

请求转换：Responses API → Chat Completions

这是代理最核心的函数。Codex 发来的请求是 OpenAI Responses API 格式 — 使用 input 数组和 instructions 字段。DeepSeek 只接受 Chat Completions 格式 — 使用 messages 数组。两侧的数据结构完全不同，需要逐字段翻译。

Responses API（Codex 发来） Chat Completions（发给 DeepSeek）
{ instructions: "...", input: [...] } → { messages: [{role:"system",...}, ...] }
input 是数组，支持多种格式 → messages 统一为 {role, content}
max_output_tokens → max_tokens（字段名不同）
model: "deepseek-v4-pro[1m]" → 去掉 [1m] 后缀
JavaScript 

function translateRequest(body) {
  const messages = [];

  // instructions → system message
  if (body.instructions) {
    messages.push({ role: 'system', content: body.instructions });6
  }

  const input = body.input;
  if (typeof input === 'string') {
    messages.push({ role: 'user', content: input });7
  } else if (Array.isArray(input)) {
    for (const item of input) {

      // ── 格式 1: 纯字符串 ──
      if (typeof item === 'string') {
        messages.push({ role: 'user', content: item });8
      }

      // ── 格式 2: {role, content} 标准消息 ──
      } else if (item.role) {9
        if (Array.isArray(item.content)) {
          // content 可能是 [{type:'output_text', text:'...'}]
          const text = item.content
            .filter(c => c.type === 'output_text' || c.type === 'input_text')
            .map(c => c.text).join('');
          messages.push({ role: mapRole(item.role), content: text });
        } else {
          messages.push({ role: mapRole(item.role), content: item.content || '' });
        }

      // ── 格式 3: {type:"input_text", text:...} ──
      } else if (item.type === 'input_text' || item.type === 'input_image') {10
        messages.push({ role: 'user', content: item.text || '[image]' });
      }

      // ── 格式 4: {type:"message", ...} ──
      } else if (item.type === 'message') { ... }
    }
  }

  // 去掉 [1m] 后缀 — DeepSeek 不认这个格式
  const model = (body.model || 'deepseek-v4-pro').replace(/\[.*\]/g, '');11

  const result = { model, messages, stream: body.stream || false };
  if (body.max_output_tokens) result.max_tokens = body.max_output_tokens;
  if (body.temperature != null) result.temperature = body.temperature;
  if (body.top_p != null) result.top_p = body.top_p;
  return result;
}
注解 6

instructions → system 消息

Responses API 把系统提示词放在顶层 instructions 字段；Chat Completions 把它作为第一条 role: "system" 消息。这是两套 API 最根本的结构性差异。

注解 7

简洁路径：纯文本输入

如果用户只发了纯文本（如 "hi"），input 是一个字符串，直接包装成 user 消息。

注解 8

格式 1：数组中的纯字符串

input: ["第一条消息", "第二条消息"] — 每项就是一个 user 消息。

注解 9

格式 2：标准消息对象

{role: "user", content: "..."} 或 {role: "assistant", content: [{type: "output_text", text: "..."}]} — content 可能是字符串或数组，需要分别处理。多轮对话中的历史消息用这种格式。

注解 10

格式 3：Content Block

{type: "input_text", text: "hi"} — Responses API 的 content block 格式，没有 role 字段。这种格式在旧版代理中被静默丢弃，导致 codex 没响应 — 这是踩过的坑。

注解 11

模型名后缀去除

Codex 在模型名后加 [1m] 表示 1M 上下文窗口。正则 /\[.*\]/g 去掉这个后缀，因为 DeepSeek API 不识别它。

§4

非流式响应转换：Chat Completions → Responses API

当 Codex 以非流式模式（stream: false）请求时，DeepSeek 一次性返回完整 JSON。需要把 Chat Completions 的响应结构逆向翻译回 Responses API 格式。

JavaScript 

function translateResponse(chatResp, model) {
  const choice = chatResp.choices?.[0];

  const content = choice.message?.content || '';
  const reasoning = choice.message?.reasoning_content || '';12

  const output = [];
  if (reasoning) {
    output.push({
      id: genId('rs'),
      type: 'reasoning',
      content: [{ type: 'reasoning_text', text: reasoning }],
    });13
  }
  output.push({
    id: genId('msg'),
    type: 'message',
    role: 'assistant',
    content: [{ type: 'output_text', text: content }],
  });

  // usage 字段名也不一样
  return {
    id: chatResp.id || 'resp_' + Date.now().toString(36),
    object: 'response',
    output,
    usage: {
      input_tokens: chatResp.usage?.prompt_tokens || 0,
      output_tokens: chatResp.usage?.completion_tokens || 0,
      total_tokens: chatResp.usage?.total_tokens || 0,14
    },
  };
}
注解 12

推理内容单独提取

DeepSeek 的推理模型在 reasoning_content 字段返回思考过程，和正文 content 是分开的。Responses API 用 type: "reasoning" 输出项来表示。

注解 13

输出项 ID

每个输出项都需要唯一的 id。Codex 用这些 ID 来追踪和管理输出 — 比如在 UI 中折叠/展开推理块。

注解 14

Usage 字段映射

Chat Completions 用 prompt_tokens / completion_tokens，Responses API 用 input_tokens / output_tokens。字段名不同但含义完全一致。

§5

流式块转换

流式模式下，DeepSeek 以 SSE 格式逐块返回。每个 chunk 包含 choices[0].delta，其中可能同时有推理内容和正文内容。代理将每个字段映射为对应的 Responses API SSE 事件。

JavaScript 

function translateStreamChunk(parsed) {
  const choice = parsed.choices?.[0];
  const delta = choice.delta || {};
  const events = [];

  if (delta.reasoning_content) {
    events.push({
      event: 'response.reasoning_text.delta',
      data: { type: 'response.reasoning_text.delta', delta: delta.reasoning_content },
    });15
  }

  if (delta.content) {
    events.push({
      event: 'response.output_text.delta',
      data: { type: 'response.output_text.delta', delta: delta.content },
    });
  }

  if (delta.tool_calls) {
    for (const tc of delta.tool_calls) {
      events.push({
        event: 'response.function_call_arguments.delta',
        data: { call_id: tc.id, delta: tc.function?.arguments || '' },
      });16
    }
  }

  return events.length > 0 ? events : null;
}
注解 15

推理 & 正文分离

DeepSeek 的一个 SSE chunk 可能同时包含 reasoning_content（思考过程）和 content（最终回答）。两者被映射为不同的事件类型，Codex 才能分别在 UI 中渲染。

注解 16

工具调用支持

当模型调用工具（如读取文件、执行命令）时，DeepSeek 在 delta.tool_calls 中增量返回函数名和参数。代理将其转为 function_call_arguments.delta 事件。

§6

SSE 事件生命周期

这是整个代理最精妙的部分，也是踩坑最多的地方。Responses API 的流式协议严格定义了一个事件序列。缺少任何一个事件，Codex 都会认为响应不完整。以下是从收到第一个 DeepSeek chunk 到响应结束的完整事件链。

Step 1
response.created
声明响应对象创建，分配 response_id
→
Step 2
response.in_progress
标记响应进入生成状态
→
Step 3
output_item.added
声明输出项（reasoning / message），分配 item_id
→
Step 4
*_text.delta × N
逐块发送推理和正文增量，携带 item_id
→
Step 5
*_text.done
标记内容生成完毕，附完整文本
→
Step 6
output_item.done
标记输出项完成，附最终状态
→
Step 7
response.completed
响应完成，携带完整 output 数组和 usage

关键洞察： 最初版本只发了 Step 4 的 delta 事件，缺失了 Step 1-3 和 5-7。Codex 报 "stream disconnected before completion: stream closed before response.completed" — 报错信息精确指出了缺失的事件。 第二次修复加了 response.created 和 response.completed，但忘了 output_item.added 和 item_id 关联。Codex 不报错但也不显示任何内容 — 它收到了响应对象，但因为没有 output_item 声明，不知道 delta 事件属于哪个输出项。

§7

HTTP 服务器与路由

使用 Node.js 内置 http 模块创建服务，零外部依赖。处理 CORS、路由分发、请求/响应转发。

JavaScript 

// CORS — Codex 从本地文件运行，跨域请求需要这些头
res.setHeader('Access-Control-Allow-Origin', '*');17
res.setHeader('Access-Control-Allow-Headers', 'Content-Type, Authorization, x-stainless-*');

// 路由：支持三种路径格式
const isResponsesPath = req.method === 'POST' &&18
  (req.url === '/responses' ||
   req.url === '/v1/responses' ||
   req.url === '/openai/v1/responses');

// 流式响应 — Content-Type 必须是 text/event-stream
res.writeHead(200, {
  'Content-Type': 'text/event-stream',
  'Cache-Control': 'no-cache',
  Connection: 'keep-alive',19
});

// 兜底：如果流异常结束（没有 finish_reason），补发完成事件
dsRes.on('end', () => {
  if (!completed) {
    // 补发所有缺失的 .done 和 .completed 事件
    sendCompletionEvents(...);20
  }
  res.write('data: [DONE]\n\n');
  res.end();
});
注解 17

CORS 头

x-stainless-* 是 OpenAI SDK 使用的自定义请求头。不加这个头，Codex 的预检请求（OPTIONS）会失败。

注解 18

多路径兼容

不同版本的 Codex 或不同的 provider 配置可能使用不同路径。三种路径覆盖所有情况。

注解 19

SSE 必需头

text/event-stream 告诉客户端这是 SSE 流。 no-cache 防止代理/CDN 缓存流内容。 keep-alive 保持连接不关闭。

注解 20

防御性兜底

正常情况下 DeepSeek 会在最后一个 chunk 携带 finish_reason，代理据此触发 response.completed。但如果网络异常或 API 行为变化导致流在 finish_reason 出现前就结束了，end 事件会兜底补发完成事件。Codex 永远不会卡在 "等待完成" 状态。
